## Q1 - Props
**`QuestionCard.vue` receives the current question as a prop. Explain what a prop is and why we pass data down from the store via the parent rather than importing `useGameStore` directly inside `QuestionCard`.**

A prop (property) in Vue is a way for a parent component to pass data down to a child component. The child receives the data as an input and uses it to render its UI. In this project, `QuestionCard.vue` receives the current question as a prop from its parent component. The prop contains the question text and the array of answer options. Vue follows a one-way data flow, meaning data flows form parent to child. The parent or the store owns the state, and the child component simply displays the data it receives. Instead of importing `useGameStore` directly inside `QuestionCard.vue`, the parent passes the question as a prop which keeps `QuestionCard` focused only on displaying the question and emitting user actions. Using props is preferred for presentational components because it keeps them simpler, reusable, and less tightly coupled to global state. The component can display any question data it receives without needing to know where the data comes from.

## Q2 - $emit
**When the user clicks an answer button, `QuestionCard` emits an event. Explain what `$emit` does, how the parent listens for it, and what would happen if you forgot to handle the emitted event in the parent.**

In Vue, `$emit` is used by a child component to send an event to its parent component. It allows the child to notify the parent that something happened, such as a user interaciton. In this project, `QuestionCard.vue` uses `$emit` when a user clicks an answer button and the component eits an event (for example "answer") along with information about which answer was selected. The parent component listens for this event using an even listener in the template for example `QuestionCard @answer="submitAnswer" />. When the event is emitted, the parent receives it and calls the submitAnswer action from the useGameStore to check whether the answer is correct and update the game state. If the parent did not handle the emitted event, the click would still occur but nothing would happen in the game logic. The score would not update and the game would not move to the next question because the parent component would never receive the event or trigger the store action.

## Q3 - Pinia store
**Before Pinia, `currentIndex`, `score`, and `gameState` all lived in `App.vue`. Explain what problem this causes as the component tree grows, and how moving state into a Pinia store solves it.**

Before using Pinia, the game state variables such as `currentIndex`, `score`, and `gameState` were stored inside `App.vue`. This means that `App.vue` owned the state, meaning it was responsible for storing and updating those values. As the component tree grows, this can create problems because other components may also need access to that same data. To share the state, the parent would have to pass the data through multiple layers of components using props. This process is called prop drilling, where data is passed down through several intermediate components that may not even need to use it themselves. This can make the code harder to manage and understand. Moving the game state into a Pinia store solves this problem by creating a centralized place where the state is stored and managed. The Pinia store (for example useGameStore) owns the state, meaning it is responsible for holding and updating values like `score`, `currentIndex`, and `gameState` through actions such as `submitAnswer()` or `nextQuestion()`. Components can then access the store directly instead of passing data through multiple layers of props, which keeps the component stucture cleaner and easier to maintain.

## Q4 - Vue Router
**Explain the difference between a traditional multi-page website and a Single-Page Application. What does `<router-view>` do, and why does navigating between routes not reload the page?**

A traditional multi-page website loads a completely new HTML page from the server every time the user navigates to a different page. Each link or navigation action causes the browser to reload the entire page, including HTML, CSS, and JavaScript. A Single-Page Application works differently where the browser loads one main HTML page at the beginning and the JavaScript dynamically updates what is shown on the screen as the user nabigates through the app. In Vue applications, Vue Router manages navigation between different views without reloading the page. The `<router-view>` component acts as a placeholder in the layout where the component for the current route will be displayed. When the route changes (for example from `/` to `/play`), Vue Router replaces the component inside `<router-view>` with the one associated with the new route. Because the application is already loaded in the browser, navigation between routes only updates the displayed component using JavaScript, rather than requesting a completely new page from the server. This is why the page does not fully reload when navigating between routes.

## Q5 - v-if vs v-show
**The game uses `v-if` to switch between screens. Explain the difference between `v-if` and `v-show`. Why is `v-if` the better choice here rather than `v-show`?**

`v-if` and `v-show` are both used in Vue to conditionally display elements, but they work in different ways. `v-if` completely adds or removes elements from the DOM depending on whether the condition is true or false. If the condition is false, the element does not exist in the DOM at all. `v-show` keeps the element in the DOM but toggles it visibility using the CSS `display` property. The element is still present but hidden. In this game, `v-if` is the better choice because the application switches between different screens, such as the start screen, the question screen, and the score screen. Since only one of these screens should exist at a time, `v-if` ensures that inactive components are removed from the DOM, which avoids unnecessary rendering and keeps the application state cleaner. Using `v-show` would keep all screens in the DOM at the same time and only hide them visually, which is unnecessary for this type of screen-based navigation.
